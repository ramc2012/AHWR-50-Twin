# CRMF Central Portal — UI Improvement Requirements

## 1. Executive summary

The CRMF portal is a functionally rich, visually coherent monitoring UI (consistent dark ops theme, live fleet map, EDR strip charts, role-aware nav) that currently sits at **solid demo/prototype maturity — not yet 24/7 control-room production grade**. Verified review across four dimensions found: (a) **safety-semantics defects** — ESD "ACTIVE" renders green, mud losses are never highlighted, and the EDR shows a green LIVE badge over frozen data; (b) **missing resilience** — one failed poll can permanently blank the primary rig view, there is no top-level error boundary, and loading/empty/error states are silent or misleading; (c) a **structural data gap** — alarm triage operates on aggregate counts with no discrete alarm records anywhere in the stack; and (d) accumulating **performance and consistency debt** (unbatched socket-driven re-renders, no code splitting, duplicated formatters/chips/colors). All 43 requirements below were confirmed against source; roughly a third are small, high-leverage fixes.

## 3. Top 5 quick wins

All high-severity, small-effort, verified line-exact:

1. **UI-01 — ESD "ACTIVE" must never be green.** One enum map + one banner; inverted safety color on an emergency-shutdown indicator is the single worst defect found.
2. **UI-02 — Honest LIVE badge and frozen-axis fix in the EDR.** A rig silent for 10 minutes currently shows a green LIVE badge over a plausible-looking frozen strip.
3. **UI-05 — RigDetail must survive one failed poll.** Clear the error on success; a transient blip currently kills the primary surveillance view until the operator navigates away.
4. **UI-06 — Top-level ErrorBoundary.** The reusable boundary already exists; it just is not mounted where it protects the 24/7 wall.
5. **UI-03 — Units/ranges from the metric catalog.** ft-vs-m and a 10x torque unit error on an operator-facing HMI, fixed by exporting the existing lookup.

(UI-04 and UI-07 are equally small and worth bundling into the same sprint.)

## 4. Larger initiatives

**UI-16 — Discrete alarm records through the whole stack (Large).**
This is the portal's core structural gap: triage today works on per-rig count snapshots because no individual alarm (tag, message, timestamps, ack state) exists in the sync contract, ingest schema, API, or UI. Fixing it touches the edge contract, TimescaleDB schema, two backend APIs, and two UI surfaces — but until it lands, the "Alarm Command Centre" cannot actually triage alarms, only rigs. Keep it read-only per the monitoring-only rule; ack stays at the edge but per-alarm ack state becomes visible centrally.

**UI-43 — Spike-preserving decimation with envelope rendering (Large).**
Avg-only bucketing to ~400 points erases exactly the transients an EDR exists to show (pressure kicks, torque spikes, overpulls) — a 4 h window averages 36 s buckets. The backend half is cheap (telemetry_1m already stores min/max); the real work is the sample-shape change through EdrView's live-merge buffer and the SVG band rendering. High operator value for trend forensics and well-run replay.

**Real-time data-path modernization (bundle: UI-14 + UI-35 + UI-40, Medium each, coherent as one program).**
Today the pipeline is per-rig socket deltas triggering full-fleet sorts and unmemoized context broadcasts, while rig telemetry paradoxically arrives by 2 s REST polling that rebuilds a 6 h buffer per tick. Executed together — batched fleet flushes, per-rig socket rooms, append-only ingest — these three changes turn steady-state rendering cost from O(fleet × event-rate) to O(changed rigs) and remove up to 2 s of display latency, which is the right foundation before scaling past ~50 rigs.
